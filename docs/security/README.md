# Securing what runs behind eggrd

Guidance for people who use eggrd to protect an application: how to harden it, what to log and
keep, and what to do when something goes wrong. Written for eggrd **0.7.0 and 0.7.1**, and measured
on 0.7.0 (`mancube/eggrd:0.7.0@sha256:b19278b379a457e626954e148effffa2fe559613d55ff497fdaa862c8c4096f6`). Run
**0.7.1**, pinned by the index digest given in its release notes: it fixes the Host-rule bypasses
and the upstream-credential logging described in EG-HARD-082 and EG-HARD-165.

| Document | For | Use it to |
|---|---|---|
| [HARDENING-CHECKLIST.md](HARDENING-CHECKLIST.md) | whoever deploys and audits the edge | Work through 77 items with stable IDs (`EG-HARD-001`…), each with why, the exact config, how to verify it, its severity and the reference setup that implements it |
| [checklist.yaml](checklist.yaml) | tooling | The same items, machine-readable: track them in a ticket system or a compliance sheet. Generated by [tools/gen-checklist-yaml.mjs](tools/gen-checklist-yaml.mjs) (`--check` fails on drift; the source repository's CI runs it) |
| [LOGGING-AND-EVIDENCE.md](LOGGING-AND-EVIDENCE.md) | operators, the security team | Know every field and event eggrd writes, what to keep and for how long, how to ship it, and run ready-made jq, LogQL and CloudWatch queries |
| [INCIDENT-RESPONSE.md](INCIDENT-RESPONSE.md) | on-call, the incident commander | Triage, preserve evidence (scripts for Docker and Kubernetes), contain with the levers eggrd has (each timed), recover, and follow one of eight playbooks |
| [examples/](examples/) | everyone | A hardened config, Vector / Fluent Bit / CloudWatch agent configs, extra Prometheus alerts with tests, a jq library, the evidence scripts |

Start with the [reference deployments](../../deploy/reference/): each is a tested setup whose README
lists the hardening it applies. This corpus says why each setting matters, how to check it, and
what to do when it was not enough.

## Conventions

- **IDs** are `EG-HARD-NNN`, grouped by layer in blocks of twenty (network 001–019, TLS 020–039,
  …). An ID is never reused or renumbered, so it can be cited from a ticket or an audit.
- **Severity**: Critical, High, Medium, Low.
- **[App]** marks work the edge cannot finish alone (Host validation, real 404s, a CSP nonce).
- **[0.8]** marks a workaround for something 0.8 plans to fix; **[Gap]** something no release plans
  yet, with what to do instead.
- Examples use `app.example.com`, documentation address ranges (RFC 5737: `192.0.2.0/24`,
  `198.51.100.0/24`, `203.0.113.0/24`) and private ranges. Nothing here comes from a real
  deployment's identifiers.

## What real deployments taught

The items are grounded in reviews of real eggrd deployments and their logs. Generalised, with no
identifiers:

- **Scanners are most of the traffic.** Over six weeks of one site, a third of all requests were
  answered `429`, and clients sent thirteen thousand more requests after their first 429. Per-IP
  limits keep scanners off the app; they do not make them stop (EG-HARD-120).
- **Many scanners never repeat.** 419 of 2,181 addresses probed; 192 of those sent three requests or
  fewer. No per-IP limit sees them; refusing the probe on its first request does (EG-HARD-083,
  EG-HARD-124).
- **What they look for:** `.env` files (the largest category by far), PHP and `phpinfo`, WordPress
  (one endpoint tried in more than a dozen path-mangling variants: case, doubled slashes, `%2f`,
  `/..;/`, trailing slashes, directory prefixes), config files, admin panels, SSL-VPN appliances, `.git`, SAP, cloud
  credential files, CGI, traversal; with `CONNECT`, `PROPFIND`, `SSTP_DUPLEX_POST` and random verbs.
- **Soft-200s hide the difference between a hit and a miss.** An app's catch-all route answered
  about one in seven `.env` probes with `200` and its HTML shell: nothing leaked, but every scanner
  logged a hit (EG-HARD-146).
- **IP-literal SNI is noise**: 14% of one edge's log lines (EG-HARD-027).
- **An app's internal metrics were routed to the internet** through a forgotten prefix and scraped
  by strangers (EG-HARD-003).
- **A WAF left in report mode protects nothing**: the same SQL-injection probe was refused by one
  edge and reached the app through another. The report → block review itself was uneventful: 54
  matches in 13 hours, all scanners, no false positive from body inspection on an ingest API
  (EG-HARD-080).
- **Containers ran unhardened** (no restart policy, all capabilities, writable root, no limits, a
  floating tag) beside a fully hardened one (EG-HARD-200–206, 220).
- **Hot reload silently did nothing**: single-file mounts and a checksum annotation stuck at its
  placeholder meant edits never reached the edge (EG-HARD-242).
- **Unknown keys load silently**: `allowed_hosts`, `[log] level` and a misspelt `inspect_header`
  all passed `doctor` and did nothing (EG-HARD-240).
- **0.7.0 fixed three security bugs** found by reviews before the release: a duplicated
  credential header checked with one value and forwarded with another; the client-written
  `X-Forwarded-For` entry taken as the client; client-written `X-Real-IP`, `Forwarded`,
  `True-Client-IP` and `X-Forwarded-Host` reaching the app (EG-HARD-041, 101, 161, 241).

## Known 0.7 gaps, and their workarounds

| Gap | Workaround until fixed | Item |
|---|---|---|
| No `allowed_hosts`: any `Host` is served | A WAF Host rule (`deploy/reference/tools/host-rule.sh`), plus Host validation in the app | EG-HARD-082, 161 |
| `trust_forwarded_for` believes the header from every peer (0.8: `trusted_forwarders`) | Only the balancer may reach the traffic port | EG-HARD-001 |
| No automatic ban or jail | `[access] deny` from the log, fail2ban-style automation, a cloud WAF | EG-HARD-124 |
| `doctor` ignores unknown keys | Review keys against the reference; test the behaviour | EG-HARD-240 |
| The ACME `account.json` and ledger are written `0644` | `chmod 600` after every start | EG-HARD-180 |
| The redirect `Location` uses `server.port` | Listen on 443 inside the container | EG-HARD-021 |
| Hot reload does not fire on single-file or host-VM mounts; on a ConfigMap edited in place it fired on k3s v1.31.14 (27–62 s, at the kubelet's sync), did not in one run on k3s v1.33.4 with the Docker runtime, and is untested elsewhere | Mount the directory; roll the pods on change | EG-HARD-242 |
| No per-path authentication, no maintenance response | A WAF path rule, a second edge, or the app | EG-HARD-105, INCIDENT-RESPONSE.md |
| `ip_denied` counted as `outcome="other"`; WAF events carry no `request_id`; no metric for config reloads | Count denials and reloads from the log; join WAF events on address, path and second | LOGGING-AND-EVIDENCE.md |
| Upstream error lines print credentials embedded in upstream URLs | Fixed in 0.7.1 (#1748): upgrade. On 0.7.0, no `user:pass@` in upstream URLs | EG-HARD-165 |
| The WAF Host rule does not see an HTTP/2 `:authority` (h2c prior knowledge on the plain listener: a forged authority gets 200 and becomes `X-Forwarded-Host`), nor a request with no `Host` at all (200, HTTP/1.0 or 1.1, plain or TLS) | Fixed in 0.7.1 (#1748): upgrade. On 0.7.0: terminate TLS in eggrd or fence the plain port to the balancer; validate the host in the app and refuse requests without one | EG-HARD-082, 161 |
| `[log.ship] headers` (a collector token) has no `_FILE` or environment form, so the token sits in the config | A mutual-TLS or loopback receiver that needs no token | LOGGING-AND-EVIDENCE.md, EG-HARD-181 |
| No image signature, SBOM or provenance published | Pin the digest; generate your own SBOM and scan | EG-HARD-221 |

## What was tested

Everything ran on `mancube/eggrd:0.7.0` (the digest above) with Podman, a Docker 28 daemon (dind)
and k3s v1.31.14, on 2026-11-04. Nothing ran against a production system; the "real deployment"
statistics above come from earlier reviews.

| Claim | How it was checked | Result |
|---|---|---|
| Every config key in the corpus exists | Every TOML block (checklist, logging, incident response, `examples/edgeguard.hardened.toml`) parsed and walked against the serde structs of `src/config.rs` at 0.7.0, by a checker that also flags `inspect_header`, `[log] level` and `allowed_hosts` | 0 unknown keys |
| Every config block loads | `edgeguard doctor` from the 0.7.0 image on each of the 48 blocks, with a throwaway PKI at the paths the blocks name and `EDGEGUARD_API_KEYS_FILE` set (as the API-key blocks prescribe) | 0 errors on every block (warnings listed by doctor are expected: `auth.mode = "none"`, no redirect listener, …) |
| Metric, label, log-field, event and alert names | Read from `src/` and `monitoring/` at the current main, then seen in the live edge's `/__edgeguard/metrics` and stdout | All present as written |
| The containment levers | Each applied to a running 0.7.0 edge (directory-mounted config) while a client polled every 50 ms: `[access] deny`, WAF report → block with custom path and header rules, a route rate limit, `allow_methods`, a path taken offline (and the route-removal trap), auth on (API key, JWT), API-key and JWT-secret rotation, a pool target ejected, a bad reload; a restart; on k3s, an in-place ConfigMap edit and a pod roll | Times in INCIDENT-RESPONSE.md. Not measured: revoking a client certificate, stopping the edge |
| Path rules against spelling variants | The `offline-admin` and `never-valid-paths` patterns against 28 variants (`//admin`, `/ADMIN`, `/./admin`, `/admin;x`, `/%61dmin`, `//.env`, `//WP-LOGIN.PHP`, …) on a live 0.7.0 edge | Every variant of a protected path 403; the documented non-matches 200 |
| The Host rule per protocol | HTTP/1.1 and `--http2` over TLS, h2c prior knowledge and `Upgrade: h2c` on the plain listener, and requests without `Host` | 403 except h2c prior knowledge and no-Host requests (200): documented in EG-HARD-082 |
| `X-Forwarded-For` with `ip:port` entries | nginx stand-ins writing `ip:port` and `[ipv6]:port` (the Azure Application Gateway v2 form), one replacing and one appending | Port stripped, `result="used"`, the client resolved |
| The jq queries | Run with jq 1.7.1 against the edge's own stdout from a synthetic traffic mix (1,139 lines: users, a sweeping scanner, 39 hit-and-run probers, path-mangling variants, junk methods, WAF hits in report then block mode, credential stuffing, spoofed `X-Forwarded-For`, app 5xx, API-key and JWT principals, TLS failures), and against the Vector-normalised archive | All returned the expected rows |
| The LogQL queries | Run against Loki 3.4 fed by the Vector pipeline and by Fluent Bit | All parsed and returned series |
| The CloudWatch Logs Insights queries | Written to the documented grammar | **Not run** (no AWS account used) |
| Shipping | Vector 0.46 (`[log.ship]` + file → Loki + an S3 emulator), Fluent Bit 3.2 (CRI file → Loki) run end to end; the CloudWatch agent config validated as JSON; OTLP blocks pass doctor | Vector and Fluent Bit delivered; the Vector receiver on loopback with Basic auth (401 without it) and the `unparsed` dead letter re-run after the review; awslogs, the CloudWatch agent and OTLP not run |
| Mirror safety | `scripts/ossync-check.sh` on the staged public cut, and every relative link and anchor in the corpus resolved inside that cut (`tools/check-links.mjs`; the source repository's CI runs both on every change to the corpus) | Scan clean; 120 links, 0 broken |
| Extra alerts | `promtool test rules examples/prometheus-security-rules.test.yml` | Pass |
| Evidence scripts | `collect-evidence-docker.sh` against a 0.7.0 edge on Docker 28; `collect-evidence-k8s.sh` (with the PVC snapshot) against the reference hostPort deployment on k3s | Bundles complete, `sha256sum -c` clean |
| Redaction | Requests with `?code=…&state=…`, `?email=…`, a JWT, a percent-encoded `token`, a token in a path | Query values redacted, the path segment not (as documented) |

Not tested here: anything on AWS, GCP or Azure (the balancer-specific items rely on the reference
setups' local stand-ins and the providers' documentation), ACME issuance (covered by the
reference's Pebble runs), CRL revocation timing, and the CloudWatch side of every query.
